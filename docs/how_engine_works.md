# Как работает Huynity

Huynity хранит мир как сцену, обновляет его небольшими шагами времени и передаёт рендереру
подготовленное описание кадра. Рендерер рисует изображение, а оконный адаптер показывает его
и возвращает события клавиатуры и мыши. Всё это работает внутри одного приложения через
обычные вызовы C++ и структуры данных: сетевого протокола между компонентами нет.

Документ описывает текущую рабочую копию, включая OpenGL-рендерер, а не только последний коммит.
[Интерактивная схема](../.archify/architecture-huynity-20261117-014248/huynity.html) показывает
основной путь и подписывает данные на связях. Math и Image объяснены в карточках схемы:
это общие типы, а не самостоятельные процессы. Русский интерфейс просмотрщика подготовлен
агентом на основе каталога Archify; отдельная редакторская проверка перевода не проводилась.

## Кто за что отвечает

| Компонент | Простыми словами | Через что общается |
| --- | --- | --- |
| Пример или игра | Создаёт мир и задаёт поведение | `Engine::create`, `scene()`, `onUpdate`, `input`, настройки камеры и света |
| Engine | Собирает компоненты и ведёт главный цикл | Обычные вызовы C++; хранит Scene, WindowAdapter, рендереры и объекты Runtime |
| Math | Считает координаты, векторы и преобразования | `Point`, `Vector`, `Transform`, функции `compose`, `inverse` |
| Object Library | Создаёт и проверяет геометрию, превращает фигуры в треугольники | `TypedParams` / `ObjectSpec` → `Geometry`; `tessellate` → сетка; ошибки через `std::expected` |
| Core / Scene | Владеет объектами сцены, их связями и состоянием | `ObjectId`, методы `set…`, команды, представление `SceneView` |
| Core / RenderPreparation | Выбирает нужные объекты и собирает кадр | Читает Scene; выдаёт `RenderSnapshot` |
| Render Contracts | Общий язык между подготовкой и рисованием | `Camera`, `Material`, `MeshResource`, `DrawItem`, `World3DPass`, `World2DPass`, `Hud2DPass` |
| Renderer | Превращает снимок в изображение | `render(const RenderSnapshot&)` у OpenGL; снимок и `ImageBuffer&` у программного рендерера |
| Image | Владеет массивом пикселей изображения | Перемещаемый `ImageBuffer`, RGBA8, размеры и шаг строки `stride` |
| Runtime | Считает шаги симуляции и управляет жизнью кадров | `FixedStepUpdate`, `FramePipeline`, пул буферов; для отдельного пути — `RendererPort` и завершения |
| Window Adapter | Обслуживает окно, ввод и показ изображения | `pollEvents` → `InputEvent`; `present(unique_ptr<ImageBuffer>)` либо GL-контекст и `swapBuffers` |
| Renderer Actor adapter | Тестирует передачу владения кадром и завершения | `RenderFrame`, `trySubmit`, `CompletionChannel`, `FrameReady` / `FrameFailed`; сейчас реализован fake |

Геометрия и экземпляр объекта — разные вещи. Object Library знает, что такое сфера или сетка,
но не назначает сценические `ObjectId`. Scene добавляет положение, материал, видимость,
родителя и идентификатор. Несколько экземпляров могут разделять геометрию.

## Один кадр по шагам

1. **Получить ввод.** Engine вызывает `WindowAdapter::pollEvents`. SDL-события переводятся
   в собственные `InputEvent`. `InputState` запоминает зажатые клавиши и кнопки, положение
   курсора и накопленные смещения мыши. Изменение размера окна обновляет размеры поверхности.
2. **Обновить мир.** `FixedStepUpdate` накапливает прошедшее время и вызывает `onUpdate`
   с постоянным шагом — по умолчанию 1/60 секунды. За один кадр может быть ноль, один
   или несколько таких вызовов. Engine ограничивает догоняющие обновления пятью;
   избыток полных шагов отбрасывается, чтобы зависание не породило бесконечное догоняние.
3. **Выполнить обработчик кадра.** Если задан `onFrame`, он получает долю оставшегося
   шага. Это позволяет приложению делать интерполяцию, но Engine не интерполирует все
   объекты автоматически.
4. **Подготовить сцену.** Core обновляет мировые преобразования и ограничивающие объёмы.
   Преобразование ребёнка складывается с преобразованием родителя. Флаги изменений
   помогают переиспользовать уже рассчитанные данные.
5. **Собрать снимок.** RenderPreparation отбрасывает ненужные объекты, получает сетки
   из кеша тесселяции и собирает таблицы ресурсов, материалов и команд рисования.
   При включённых тенях учитываются также подходящие объекты вне камеры: они могут
   отбрасывать тень на видимую поверхность.
6. **Нарисовать и показать.** Engine выбирает доступный путь рендеринга, описанный ниже.
   В конце кадра накопленные смещения мыши и колеса сбрасываются; состояния зажатых
   клавиш остаются до событий отпускания.

Исходный порядок находится в [Engine::step](../engine/core/src/engine.cpp),
правила шага времени — в [FixedStepUpdate](../engine/runtime/include/huynity/runtime/fixed_step_update.h).

## Два пути рисования

### OpenGL — основной путь нативных примеров

При запуске Engine получает окно. Если оно предоставляет GPU-поверхность и удалось
создать `GlRenderer`, дальнейшие кадры идут в него синхронно:

`RenderSnapshot → GlRenderer → framebuffer OpenGL → WindowAdapter::swapBuffers()`.

Оконный адаптер создаёт GL-контекст, делает его текущим и предоставляет загрузчик GL-функций.
Рендерер загружает сетки и текстуры на GPU и переиспользует их по идентификаторам и версиям.
Обычный кадр не копируется обратно в `ImageBuffer`; отдельный `captureFrame()` делает
снимок через offscreen framebuffer и чтение пикселей.

### Программный рендерер — headless и резервный путь

Если GL-рендерер не создан, Engine берёт буфер из пула:

`RenderSnapshot + ImageBuffer → SoftwareRenderer → WindowAdapter::present() → возврат буфера в пул`.

В нативном окне готовые пиксели загружаются в текстуру для показа. `HeadlessWindow`
сохраняет последний показанный кадр без системного окна — это удобно для тестов.
При отсутствии SDL или невозможности создать нативное окно фабрика использует headless.
Ошибка создания GL-рендерера переключает Engine на программный путь; ошибка отдельного
GL-кадра только выводится в журнал и не запускает автоматическое повторное рисование на CPU.

Эти пути имеют общий вход, но не полную одинаковость эффектов: тени от источника,
процедурное небо и атмосферная дымка реализованы в OpenGL. Программный путь проверяет
геометрию, базовое освещение, глубину, текстуры и композицию, но не является побайтовым
эталоном картинки OpenGL.

## Что содержится в снимке

`RenderSnapshot` — пакет данных для одного кадра. В нём нет ссылки на изменяемую Scene.
Он содержит размеры изображения, цвет очистки, материалы, сетки и упорядоченные проходы.
Рендерер получает его по `const&` и не изменяет сцену.

- `World3DPass` содержит камеру, свет и объекты трёхмерного мира.
- `World2DPass` содержит объекты двумерного мира со своей камерой.
- `Hud2DPass` содержит экранные элементы интерфейса в пикселях.

Порядок 2D-мира относительно 3D настраивается, HUD идёт после мировых проходов.
Внутри 2D учитываются `layer` и `order`. В 3D ближайшую поверхность выбирает буфер глубины.

Сетки в снимке представлены невладеющими диапазонами `span`, но рядом хранятся
`shared_ptr<const …>` на владельцев. Поэтому удаление объекта из Scene не уничтожает
геометрию, которая ещё нужна готовому снимку. Согласованность предполагает, что приложение
не меняет разделяемые ресурсы через оставшиеся изменяемые указатели.

Определения: [Render Contracts](../engine/render_contracts/include/huynity/render_contracts/render_snapshot.h).

## Как получаются освещение и тени

Источник `DirectionalLight` задаёт направление распространения света в мировых координатах.
Камера меняет то, как мы видим сцену, но не поворачивает солнце вместе с собой.
Для освещения поверхности направление переводится в систему камеры, а для процедурного
неба направление луча камеры переводится обратно в мир.

Тени OpenGL рассчитываются методом **shadow mapping**: сначала сцена рисуется с точки
зрения первого направленного источника в карту глубины. Затем для видимой поверхности
проверяется, нет ли перед ней преграды со стороны света. Несколько соседних выборок
смягчают край; небольшой отступ `bias` уменьшает ложные тени поверхности на самой себе.

`ShadowConfig` задаёт конечный объём карты. Его центр расположен в мире; полная глубина
`depthRange` распределена по обе стороны центра. В святилище и обсерватории этот объём
закреплён на сцене, поэтому движение игрока не перемещает сетку карты теней.
Вне объёма эта карта тень не создаёт. Движущиеся объекты и изменение направления света
закономерно меняют тени. Ограниченное разрешение карты может давать ступенчатые края.

## Где здесь асинхронность

В Runtime есть отдельный транспортный контракт:

`FramePipeline → RendererPort::trySubmit(RenderFrame) → CompletionChannel → FrameReady / FrameFailed`.

`RenderFrame` передаёт владение снимком и буфером. Конвейер допускает один активный
и один подготовленный кадр — это ограничение очереди, а не бесконечное накопление работы.
После resize поколение поверхности меняется; устаревший кадр не показывается.
Буферы возвращаются через `PresentationPort`.

Сейчас `FakeRendererAdapter` моделирует принятие кадра и завершения; он сам не рисует
и не создаёт рабочего потока. Например, `window_demo` сначала вызывает программный
рендерер, затем проводит готовый кадр через этот адаптер. В обычном `Engine::step`
`trySubmit` и `CompletionChannel` не участвуют. Поэтому «рендеринг в фоне» нельзя считать
реализованным поведением основных примеров.

Исходники: [FramePipeline](../engine/runtime/include/huynity/runtime/frame_pipeline.h),
[FakeRendererAdapter](../adapters/renderer_actor/include/huynity/adapters/renderer_actor/fake_renderer_adapter.h).

## Какие архитектурные приёмы здесь использованы

| Приём | Где виден | Что даёт |
| --- | --- | --- |
| **Фасад (Facade)** | `Engine` предоставляет короткий API поверх Scene, Runtime, Renderer и Window | Примеру не нужно вручную соединять все компоненты |
| **Порты и адаптеры** | `WindowAdapter`, `PresentationPort`, `RendererPort`; нативное и headless-окно | Код опирается на контракт; платформенную реализацию можно заменить |
| **Scene graph — дерево сцены** | Родительские связи и локальные/мировые преобразования | Детали движутся вместе с родителем, например лопасти с осью мельницы |
| **Снимок состояния и команды рисования** | `RenderSnapshot` и `DrawItem` отделены от Scene | Рисование не обращается к изменяемому хранилищу объектов |
| **Фиксированный шаг симуляции** | `FixedStepUpdate` | Скорость движения считается по времени симуляции, а не числу нарисованных кадров |
| **Кеширование и dirty flags** | Bounds, тесселяция, нормали, GPU-ресурсы | Неизменившиеся данные не нужно полностью пересчитывать и загружать заново |
| **RAII и передача владения** | `unique_ptr<ImageBuffer>`, GL-ресурсы, разделяемые неизменяемые сетки | Время жизни ресурса выражено типом и освобождение связано с владельцем |
| **Ограничение очереди (backpressure)** | Активный и подготовленный слоты FramePipeline | Производитель не накапливает неограниченное число старых кадров |

Это описание наблюдаемых решений, а не утверждение, что движок целиком реализует
какой-то один архитектурный шаблон. В частности, плотное хранение объектов и ObjectId
сами по себе не означают наличие полноценной ECS — системы независимых компонентов и систем.
